# CONTEXT: MMS Procurement Monitoring System

Attach this file (with PROGRESS.md) to every build session. Last updated: 2026-11-13.

## Project
- Monitors a Purchase Order (PO) from issuance to payment for the Materials Management Section (MMS), Zamboanga City Medical Center (ZCMC). Authoritative flow: the FINAL flowchart (`MMS_PO_to_DV_Workflow.pdf`, Draft v1.0, received 2026-11-12; 4 parts + 3 exception flows + system-wide requirements). The earlier "MMS PO to DV Briefing" is superseded: where they differ the flowchart wins, and items the flowchart flags yellow/red are open, not decided.
- Owner: Vvv, the only IT person in MMS, new to React. Under 20 users. Hospital IT deploys it later on their own server (MySQL). They use Laravel.
- Dev machine: Windows, PowerShell, XAMPP (MySQL/phpMyAdmin), folder `MaterialManagementSystem`, database `material_management_system`, run with `composer dev` at http://127.0.0.1:8000.

## Stack and conventions
- Laravel + React starter kit: Inertia, TypeScript (`.tsx`), Tailwind, shadcn-style components in `resources/js/components/ui`, Fortify auth, generated route helpers imported from `@/routes/...`.
- `app/Models/User.php` uses the attribute style `#[Fillable([...])]` and `#[Hidden([...])]` (not `$fillable`). The kit has a repository pattern (`UserRepositoryInterface`; suppliers follow the same pattern with `SupplierRepositoryInterface`, both bound in `AppServiceProvider`).
- Migration files must be the full `return new class extends Migration { ... };` file, not just `up()`/`down()`.
- Roles/permissions: `spatie/laravel-permission` (teams off). Permission names are `module.action` (e.g. `po.review`). Check permissions with Gates/Policies and middleware, never `if ($user->role === ...)`. Also enforce on the server, not only by hiding buttons.
- Frontend access: Laravel shares `auth.permissions` and `auth.sections` on every page; React reads them with the `useAccess()` hook (`can('po.review')`, `canAccess('deliveries')`). Hiding is for convenience only; the server is the real protection.
- Page layout: a page sets `Page.layout = { breadcrumbs: [...] }` (as in `dashboard.tsx`). Placeholder pages use the `ComingSoon` component.
- Login: employee number (`users.employee_no`) + password. Registration and password reset are turned off; the admin creates accounts. Deactivated users (`is_active = false`) are blocked. `last_login_at` is recorded.
- Dummy logins (password `password`): DUMMY-0001 Admin, DUMMY-0002 Procurement, DUMMY-0003 PO Reviewer, DUMMY-0004 Encoder, DUMMY-0005 Inventory Team, DUMMY-0006 MMS Head, DUMMY-0007 Finance, DUMMY-0008 DV Processor, DUMMY-0009 Messenger (0003-0005, 0008, 0009 have the MMS Staff role plus a job preset). Seeders: `RolePermissionSeeder` (structural, safe in production), `DummyUserSeeder`, `SupplierSeeder`, `CatalogSeeder` and `PurchaseOrderSeeder` (demo data; all refuse to run in production).
- Logo: `public/images/zcmc.png`. Brand colors: green `#0f8a3e` / `#0b5a2b`, yellow `#f5e400`.
- Debugging tip: when a button does nothing, check the browser console (F12) first. A stale import (e.g. `@/routes/password`) once broke a whole page.
- After adding routes or changing `config/mms_access.php`: `php artisan config:clear`, `php artisan route:clear`, `php artisan wayfinder:generate`, then `npm run build` (it also catches broken imports). After adding or renaming a permission, also run `php artisan db:seed --class=RolePermissionSeeder`, otherwise the database roles keep the old permissions.
- `php artisan mms:access-matrix` prints the role-and-permission matrix from the config (add `--md` for a Markdown table) and flags unknown permission names.

## UI conventions (apply to every step)
- File placement: React pages go in `resources/js/pages/...` (Inertia resolves them from there); reusable components go in `resources/js/components/...`. Mixing them up gives a page that silently does nothing. After adding a new page file, restart `npm run dev` (or run `npm run build`).
- Confirmations are modals, never `window.confirm`: use `@/components/admin/confirm-dialog` (`ConfirmDialog`).
- Success messages are toasts: the controller redirects with `->with('success', '...')`, `HandleInertiaRequests` shares it as `flash.success`, and `useFlashToast()` (`@/components/admin/use-flash-toast`) shows it. The single `<Toaster />` is mounted in `resources/js/layouts/app-layout.tsx`; do not mount a second one. Server rule errors (for example a blocked action) come back as validation errors and are shown as a toast or under the field.
- Forms use Inertia `useForm` with a Form Request on the server; authorization is in a Policy; business rules and guards live in a Service (Controller -> Service -> Repository for core modules).
- List pages are responsive: a normal table from the `md` breakpoint up; below `md` each row becomes an expandable card (collapsed: main identifier, status badge, one key field; expanded: the other fields and the row actions). No horizontal scrolling on phones. Built once as the reusable `ResponsiveList` component; reuse it for POs, deliveries, audit log, and so on (Users and Suppliers already use it).
- Search on list pages is live: debounced (about 300 ms), server-side, no Enter key, no page reload, with a loading state and a clear (X) button. A new search goes back to page 1, pagination keeps the search, and `?search=` stays in the URL.
- Lists with filters, an Active/Closed toggle or sortable headers (PO list, 3.2): the page gives `useLiveSearch` the current filter values as `params` and changes them with `apply()`; `ResponsiveList` columns can be `sortable` (`sort`, `onSort`; on phones the page adds a "Sort by" box). The repository checks `sort` against a fixed list of allowed columns.
- The admin user pages and the supplier pages use plain URLs (`/admin/users/...`, `/suppliers/...`) instead of generated route helpers. Either style is fine; never import a helper that no longer exists.

## Roles (5) and the final flow
Roles: Admin, Procurement, MMS Staff, MMS Head, Finance. MMS Staff covers several jobs through per-user permissions: PO Reviewer, Encoder, Inventory Team, DV Processor, Messenger.

Access rules live in one file, `config/mms_access.php`: the permission list, the role defaults, the job presets, the menu sections, and retired permission names. `RolePermissionSeeder`, `DummyUserSeeder`, `AppServiceProvider`, `HandleInertiaRequests` and the admin screen read it. The MMS Staff role itself only carries a base (`po.view`, `suppliers.view`, `delay.view`, `reports.view`). A job preset lists only the job-specific permissions, and the admin screen applies it to a user with direct permissions (`syncPermissions()`). A user may hold more than one job. Receiving, Supplier, Legal, COA and UMIS have no login.

- **Part 1, Steps 1-2: PO distribution and verification.** Procurement either creates the PO in the system (sets Schedule Term and Delivery Term) or posts it in BizBox (read by the system). Procurement uploads the PO Bundle (with the supplier document checklist). A supplier may request an extension, and the PO Reviewer extends the due date. The PO Reviewer selects the PO, reviews the details, and either verifies it or escalates to the System Admin. The system sends a 3-day delivery notice (email, later). Final flowchart additions: a grace period of 3 to 7 calendar days after the due date (status updates and monitoring continue), automatic reminders during it, and access to the PO auto-closes when it ends unless the Head of MMS reopens it; automatic supplier emails for delivery obligations and termination warnings (all emails later).
- **Part 2, Step 4: delivery, receiving, IAR.** Receiving prepares the IAR on paper. The MMS Encoder enters Invoice #, IAR #, Fund Cluster, Amount, and selects the inspectors and end-user from the UMIS list, then uploads DR, OR, IAR and all required supporting documents (the list of required supporting documents is not defined yet). The system merges the files and enforces a 3-day IAR processing window. If any required document is missing, the system blocks the step.
- **Part 3, Steps 5-6: monitoring and property documents.** The PO Reviewer updates delivered items per item and per date, and the system shows running delivered and undelivered totals. The Inventory Team decides whether an item is equipment. **UNRESOLVED (flagged in the final flowchart; do not build step 6.2 until MMS answers):** the briefing rule is above PHP 50,000 unit price = PAR plus Sub-PAR (personnel from UMIS), at or below = ICS; the flowchart says PAR is mandatory for equipment, ICS applies from PHP 1,000, and below PHP 1,000 neither applies and a mandatory remarks/justification field is required. The two overlap.
- **Part 4, Step 7: DV and finance.** The DV Processor reviews the supplier checklist. The system auto-generates the DV (editable) and the IAR Transmittal. If documents are incomplete, the MMS Head may override. After printing, the status becomes "For Finance Processing" (files emailed to COA, later). MMS Staff (the Messenger job) forwards the DV to Finance; the final flowchart requires signature and photo documentation of the handover (subject to DPU clearance). Finance confirms receipt (built as a manual confirm). The final flowchart does not restate the next step (Cashier marks payment disbursed, or Finance returns the transaction with remarks); it is carried over from the briefing and still flagged. The Part 4 lane "MMS: Person B" is read as the DV Processor job.
- **Flow A, cancellation (revised in the final flowchart):** Recommendation to Terminate; an end-user submits a request for a Notice of Termination (flagged: same role as the initiator?); MMS verifies the report; NEW: the approving authority (HOPE / Head / MCC) approves or disapproves; MMS clicks the button that emails Legal (later; the email carries an upload link for the Notice); the Notice of Termination is uploaded; PO cancelled/terminated. The order of verification and approval, and what happens on disapproval, are read from the diagram and not confirmed.
- **Flow B, replacement:** select PO and items, "For Replacement", advance notice to the supplier (email, later), the Advance Notice Letter from OMCC must now be uploaded (the flowchart files it under termination documentation; to confirm), Pull-Out Form, replacement received with remarks and dates.
- **Flow C, delay monitoring:** day count and overdue indicator, grace period (3 to 7 calendar days after the due date, with automatic reminders; access auto-closes when it ends unless the Head of MMS reopens it), then request a Notice to Terminate from Legal. An approved extension moves the due date. The DV is forwarded to Accounting only when delivery and supporting documents are complete.
- **Dashboard views:** overdue POs, total and daily transactions, PO count by status, top low-performing suppliers, pending Finance returns, open replacement requests, property documentation pending.
- **System-wide (new in the final flowchart):** dashboard monitoring of Pending DVs, DV processing status and the overall PO/DV summary; offline functionality with automatic synchronization (scope not defined, see Assumptions).
- Statuses: see decision 17 (step 1.4, approved).

## Decisions (as of 2026-11-12)
1. **Schedule Term** means scheduled delivery dates (e.g. Oct 1, Oct 15, Oct 30), so one PO may be delivered in batches (e.g. 500, then 300, then 200). **Delivery Term** is the number of days from the issue/emailed date to the due date.
2. **Data model:** PO, then PO items, then one record per delivery batch. The IAR is unique per delivery. Delivered, undelivered, and on-time status are computed, never typed. DV can link to one or more deliveries (DV per PO or per delivery is still open).
3. **BizBox:** no access yet. Keep a `PurchaseOrderSource` interface with a local implementation now and a BizBox stub. The "Fetch from BizBox" button is shown but disabled. Every PO has a local record with `source` (manual/bizbox) and `external_id`. A config flag turns BizBox on later. Do not invent BizBox fields; list what we need in an integration note.
4. **UMIS** (signers and Sub-PAR personnel) works the same way: a dummy `personnel` table behind a `PersonnelDirectory` interface now, real UMIS later.
5. **One consolidated PDF per PO.** Every uploaded document is appended in upload order (first upload = first pages). Originals are kept, and the UI shows the consolidated PDF. Wrong documents are voided or replaced with a reason, and the PDF is rebuilt. Files live on a private disk and are streamed through authorized routes.
6. **IAR numbers:** three series per year (regular `26-1398`, contract `C26-0015`, donation `D26-0001`). The system suggests the next number, staff confirm or edit, the database rejects duplicates, voided numbers are kept and never reused.
7. **Archiving:** a PO is closed when fully delivered (or cancelled/terminated) and payment is disbursed. Closed POs leave the default list but stay searchable. Never delete them.
8. **Legacy data:** start fresh from a cutoff date; import only open POs plus all old IAR numbers. The old spreadsheet stays as a read-only archive.
9. **Emails and scheduled automation come last** (Phase 11). Until then, wherever the flow says "email", fire a Laravel event or record a pending notice only. The overdue indicator is computed when pages load (no scheduler needed).
10. Skip the supplier-ownership question for now. A simple Suppliers table (name, optional email, contact person, address, is_active) is maintained by Procurement (built in step 2.1) and can change later if IT says otherwise.
11. Skip Inertia SSR. Hospital login (LDAP/SSO) and APIs are the final phase.
12. **Access model (step 0.3, extended in 2.1 and 2.2):** 37 permissions, no approval permissions (the briefing had none; the FINAL flowchart adds an approval gate in Flow A, so the approval permission and who holds it are to be decided; the permission list is unchanged for now). `cancel.finalize` covers both cancellation and overdue termination. Job presets are defined in `config/mms_access.php`. `suppliers.view` (view only) was added in 2.1 for MMS Staff, MMS Head and Finance; `suppliers.manage` (Procurement) also allows viewing. `catalog.view` (MMS Staff base, MMS Head, Finance) and `catalog.manage` (Procurement, also allows viewing) were added in 2.2.
13. **Menu and route access (step 1.1):** `config/mms_access.php` has a `sections` list (menu section => permissions, any one is enough). Each section becomes a Gate `section.<n>` (AppServiceProvider). Routes use `->middleware('can:section.<n>')`; the sidebar hides items using `auth.sections`. The Dashboard has no section (every logged-in user). Reports is the last item of Main Menu; the Exceptions and Admin groups hide themselves when empty. The `suppliers` section opens with `suppliers.view` or `suppliers.manage`.
14. **User management design (step 1.2):** a user's permissions = role permissions + direct permissions. Role permissions show ticked and locked in the admin form; job presets and per-person changes are direct permissions. The admin types passwords (no email reset, no forced change at first login for now). `users.manage` covers user actions, `roles.manage` covers role and permission changes. An admin cannot deactivate themselves or remove their own admin access, and the last active Admin cannot be deactivated or demoted.
15. **User management as built (step 1.2):** `app/Support/MmsAccess.php` is the only class that reads the shape of `config/mms_access.php` for the user screens (permission groups by module, presets, role lookups); locked role ticks come from the database roles that `RolePermissionSeeder` fills from the config, so re-run the seeder after editing the config. A job preset REPLACES a person's direct permissions; the "Job" column in the list is derived (largest preset contained in the direct permissions, MMS Staff only), not stored. Direct permissions never duplicate role permissions. A user with `users.manage` but not `roles.manage` can create users only as MMS Staff with no direct permissions and cannot change role or permissions (403). `UserService` keeps the older CRUD methods (`createUser`, `updateUser`, ...) and adds `paginate`, `create`, `update`, `setActive`, `resetPassword` and the guards (it uses `DB::transaction` directly so guard messages reach the form). Password reset also rotates `remember_token`. Deactivated users are logged out on their next request (step 1.3, `EnsureUserIsActive`).
16. **UI conventions** are in the "UI conventions" section above (modals, toasts, responsive list cards, live search, file placement).
17. **Statuses and config (step 1.4, APPROVED 2026-11-12; revised after the final flowchart):**
    - Stored statuses (enums in `app/Enums`, each with `label()`; changed only through `App\Support\StatusTransition::apply()`, which locks the row, checks the allowed move and reason, saves, and logs with `Audit::statusChanged()` using the labels, all in one transaction):
      - PO: draft -> uploaded -> verified; uploaded <-> escalated (to Admin); verified -> for_termination_approval -> for_termination (approved) or back to verified (disapproved); for_termination -> cancelled | terminated.
      - Delivery (IAR): for_uploading -> complete | voided; complete -> for_uploading | voided.
      - DV: draft -> for_finance_processing -> received_by_finance -> payment_disbursed | returned; returned -> draft.
      - Replacement item: for_replacement -> replaced.
      - A written reason is required for: escalated, for_termination_approval, disapproval, cancelled, terminated, voided delivery, complete -> for_uploading, and returned DV.
    - Derived, never stored: delivery progress (not delivered / partial / full), timing (on time / overdue / past grace), closed, property documentation pending, open replacement requests. A PO badge shows the stored status, except `verified` shows the progress label.
    - Config keys in `config/mms.php`: `property.par_threshold` 50000 and `property.ics_min_value` 1000 (both provisional, see Part 3), `iar.processing_days` 3, `delivery.notice_days` 3, `delivery.grace_period_min_days` 3 and `grace_period_max_days` 7, `delivery.grace_period_days` null (not chosen yet), `delivery.term_counting` calendar (provisional), `delivery.extension_counting` working, `uploads.max_size_kb` 10240, `uploads.allowed_extensions` pdf.
    - PHP upload limits on the dev machine (`C:\php85\php.ini`) were 2M / 8M and must be raised (about 40M / 50M); same for the hospital server.
18. **Suppliers (step 2.1, built and verified):** table `suppliers` (name unique, email, contact_person, address, is_active); Procurement (`suppliers.manage`) creates, edits and deactivates; anyone with `suppliers.view` sees a view-only list. Suppliers are deactivated, never deleted; inactive ones stay in the list with a badge, and the PO form (Phase 3) offers active suppliers only. Changes are written to the audit log (log name `suppliers`). `SupplierSeeder` adds 40 fake names in dev only.
19. **Item catalog (step 2.2, built; verification pending):** tables `item_categories` (name unique, `is_equipment`, is_active), `units` (name unique, optional short `code`, is_active) and `items` (name, category, unit, is_active; no prices or stock; unique on name + unit). Procurement (`catalog.manage`) creates, edits and deactivates; anyone with `catalog.view` sees view-only lists. Nothing is deleted; inactive rows stay in the lists with a badge, and the item form offers active categories and units only (an existing item keeps its current ones). The `is_equipment` flag is stored per category and maintained in the catalog by Procurement; the Inventory Team's Part 3 "Equipment?" decision (`equipment.decide`, step 6.2) reads it as the default. One `catalog` section opens Items, Categories and Units (sidebar group "Catalog"). Audit log name `catalog`. `CatalogSeeder` adds 8 categories, 10 units and 60 items in dev only. Later steps (PO items, deliveries) should reference `items.id` and offer active items only.
20. **PO data model (step 3.1, built and verified 2026-11-13):**
    - Tables: `purchase_orders` (`po_number` unique, `supplier_id` restrict, nullable `po_date`, `emailed_date`, `delivery_term_days`, stored nullable `due_date`, `source` manual|bizbox, nullable `external_id` (unique together with `source`), `status` default draft, nullable `closed_at`; indexes on `status`, `due_date`, `supplier_id`, `po_date` and `(status, due_date)`); `po_items` (nullable `item_id` because BizBox lines may not match the catalog, description snapshot, required `category_id` and `unit_id`, `unit_price` decimal(14,2), `quantity_ordered` unsigned integer); `po_schedules` (PO + scheduled date, unique per PO and date; dates only); `po_extensions` (PO, `extra_days`, reason, `recorded_by`, `approved_by`, `approved_at`, `old_due_date`, `new_due_date`). Models `PurchaseOrder`, `PoItem`, `PoSchedule`, `PoExtension`; enum `App\Enums\PurchaseOrderSource`; `PurchaseOrderStatus` reused. Items and schedules are deleted with their PO; extensions and suppliers/catalog rows are restricted. POs are never deleted anyway.
    - Quantities: the whole sample sheet has whole-number ordered quantities, so `quantity_ordered` is an integer. Delivered quantity is fractional on some rows (kilo, bundle), so step 5.2 must store delivered quantity as a decimal.
    - Due date: the clock starts at `emailed_date`, not `po_date`. `due_date = emailed_date + delivery_term_days`, counted by `config('mms.delivery.term_counting')`; each extension then adds its `extra_days`, counted by `extension_counting` (calendar or working; working skips Saturday and Sunday, holidays later). No emailed date, or a term of 0 or empty (donations, contracts), means no due date (null). Only `App\Support\DueDate` counts days. `PurchaseOrder::recalculateDueDate()` sets the attribute without saving: whoever changes `emailed_date` or `delivery_term_days`, or approves an extension (steps 3.3 and 3.5, in the Service), calls it in the same save. `due_date`, `status` and `closed_at` are not mass-assignable: the due date comes from `recalculateDueDate()`, the status only from `StatusTransition::apply()`. The grace period stays null; past-grace is computed later from `due_date`.
    - Extensions: a row exists only once approved. `extension.manage` records and approves in one step, so there is no pending state and the Service sets `recorded_by` and `approved_by` to the same person. The sheet only ever extends by half the term; the system stores the explicit number of days.
    - `closed_at`: a stored timestamp set only by one future method, `PurchaseOrderService::syncClosed()` (built with 7.3 and extended in 8.1), called in the same transaction after a DV becomes payment_disbursed, a PO becomes cancelled or terminated, or a delivery is voided or reopened. It sets `now()` the first time the closing rule of decision 7 holds and clears it if the rule stops holding. A cancelled or terminated PO with nothing delivered has nothing to pay and closes at once (assumed). Never typed by a user. Until deliveries and DVs exist, only the dev seeder writes it (cancelled and terminated POs). `isClosed()` and the `open()` scope read it; the default PO list (3.2) uses `open()`.
    - Schedule quantities: dates only for now. Recommended later: a separate `po_schedule_items` table (schedule date, PO item, quantity), optional per PO, added when 6.1 or 8.3 needs to tell a missed batch from a delivered one. Ask MMS whether Procurement states quantities per date.
    - Name clash: decision 3 planned a BizBox `PurchaseOrderSource` interface. The enum now owns that name, so the interface of step 3.4 is named `PurchaseOrderProvider`.
    - Offline: the app stays online (localhost in development, the hospital server later), with plain auto-increment ids and no sync. Adding offline later is possible (a client-side `uuid` column can be added and backfilled), but the real cost is in the entry screens and conflict rules, so decide before 5.1 (IAR numbering), not before 3.2.
    - `PurchaseOrderSeeder` (dev only, refuses in production, skips if POs already exist, runs after the supplier and catalog seeders): 60 POs over all 8 statuses with past, future and missing due dates, 8 extensions, 6 BizBox-source POs each with one line outside the catalog, 3 donation/contract-style POs without a due date. It writes status and `closed_at` directly (seed data only); real changes go through `StatusTransition::apply()`.
21. **PO list and detail (step 3.2, built and verified 2026-11-13):** read only, no migration, no new permission. `po.view` and the `purchase-orders` section open both pages; `PurchaseOrderPolicy` has `viewAny` and `view`. Controller -> `PurchaseOrderService` -> `PurchaseOrderRepository`. The list selects only the columns it shows, eager loads the supplier name and uses `withCount('items')` (no N+1; a test checks it). Filters: `search` (via `filterBySearch`), `status`, `supplier` (every supplier, inactive ones too), `from` / `to` (PO date), `view` (`closed`, otherwise active = `open()` scope); sorting by `sort` / `direction` against the fixed list in the repository (default due date ascending, no due date last). Invalid query values are ignored. The status badge shows the stored label only; there is an empty `OverdueBadgeSlot` component next to the due date (list and detail) for step 8.3 (computed from `due_date` and `DeliveryTiming`, not now). Detail tabs: Details, Items (line total = unit price x quantity, computed in whole centavos; PO total; lines without `item_id` are marked "Not in catalog"; money shown as PHP), Schedule (dates plus read-only extension history with approver and time), and ComingSoon for Deliveries, Documents and History. Dates are plain Y-m-d (DATE columns, no timezone shift); `closed_at` and `approved_at` go through `DisplayTime`.
22. **Create and edit PO (step 3.3, built and tested 2026-11-13):** no migration, no new permission. `po.create` opens the form; `po.edit` edits (Procurement, and the Admin for escalations). `App\Support\PoEditRule` is the one place for "may this PO be edited": draft, uploaded and escalated yes; verified and later no; BizBox source never. `PurchaseOrderPolicy::update` returns a deny message (shown on the detail page instead of the Edit button; the controller sends `edit: {allowed, reason}`, the reason only to people with `po.edit`), and the Service checks again under a row lock. A new PO is created as draft / manual / no external id; `status`, `due_date` and `closed_at` are never typed; the due date comes only from `recalculateDueDate()` whenever emailed date or term changes (approved extensions included; term 0 or empty means null). The form's due date is a browser preview using the same counting settings (`dueDateRules` prop); the server decides on save. Lines: a new line needs an ACTIVE catalog item; an existing line may keep an inactive or missing item (`item_id` null); category and unit are set by the server from the catalog item and never sent by the browser; an unchanged line keeps its stored snapshot. Schedule dates only (unique per PO). Removed lines and dates are deleted; POs are never deleted. A PO needs at least one line; PO date is required. Audit log name `po`: `created`, `updated` (old/new values, supplier by name, items and schedule summarised as added/removed/changed, nothing logged when nothing changed). Item search: `GET /purchase-orders/item-search?q=` (needs `po.create` or `po.edit`, active items only, at most 10, name starts with the text first, then contains it, minimum 2 letters). PO number rule (lenient, to confirm): trimmed, required, unique, at most 30 characters, letters, digits and `- / . _`, no spaces. `App\Support\Money` holds the centavo helpers. Toast: controllers redirect with `->with('success', ...)` through one private `saved()` method; the uploaded `use-flash-toast.ts` listens for `flash.toast`, so check which one is live if a toast does not show.
23. **BizBox-ready structure (step 3.4, built 2026-11-13, checks pending):** no migration, no permission, no network call. Interface `App\Contracts\PurchaseOrderProvider`: `source(): PurchaseOrderSource`, `isAvailable(): bool`, `fetch(string $reference): PurchaseOrderData` (throws `PurchaseOrderNotFound`; the stub throws `BizBoxNotConfigured`, message "BizBox is not configured"), `iarChecklist(string $reference): list<string>` (local provider returns `[]` because the required documents are not defined). `$reference` is the PO number (manual POs have no `external_id`). Data objects in `app/Data` (`PurchaseOrderData`, `PurchaseOrderLineData`): readonly, only fields our tables hold, dates as Y-m-d strings, unit price as a decimal string, category and unit left out on purpose. Implementations in `app/Integrations/PurchaseOrders`: `LocalPurchaseOrderProvider` (reads our database through the `PurchaseOrder` model, not the repository) and `BizBoxPurchaseOrderProvider` (stub). `AppServiceProvider` binds the interface with `bind()` by `config('mms.bizbox.enabled')` (`BIZBOX_ENABLED`, default false); when false the BizBox provider is never created. All BizBox-specific code goes only in the BizBox provider class. The create form shows "Fetch from BizBox" (disabled, tooltip plus a visible note) inside a compact dashed "Post directly in BizBox" box next to a small "Create PO in the system" box; constant `BIZBOX_FETCH_AVAILABLE` in `po-form.tsx`. Nothing in the app calls the provider yet, and no import exists: Phase 13 builds it and sets `source = bizbox` and `external_id`. BizBox-source POs stay locked for editing (decision 22). `docs/INTEGRATION-BIZBOX.md` lists what we need from BizBox and the questions for IT; the BizBox side is unconfirmed and no field names were invented.

## Assumptions to confirm with MMS or IT (do not block work)
- Delivery Term counts calendar days or working days, and how holidays are handled. The flowchart says extensions count "working calendar days only" (read as working days) and the grace period counts calendar days.
- Does a PO become overdue after its Delivery Term due date or after the last scheduled date?
